### 按 id 而不是按位置识别段落 {#paragraphs-by-id-not-by-place}

房间里的每个人都从同一个文件开始，`stampIds` 根据每个段落在文件中的位置给它一个 id：读取同一文件的人会得到相同的 id，无需互相通信。之后新建的段落会得到由创建它的编辑器生成的 id（`<client>.<n>`），因此两个人永远不会创建出相同的 id。

更改通过这个 id 指明它所涉及的段落。“在 `k3` 的偏移 12 处插入 `x`”，即使有人在 `k3` 上方添加了十个段落，含义也不变；而“在第 4 段”就不行了。

页眉、页脚、脚注和文本框是 *story*，有自己的段落和 id。对它们的更改会带上 `part`（`header`、`firstFooter`、某一节的页眉、`footnote:<id>`、`textbox:<id>`…），因此页脚中的光标、文本框中输入的文字，都会像正文一样同步给所有人。

### 更改是什么 {#what-a-change-is}

编辑器既不发送按键，也不发送整个文档。每当文档变化时，它会与上次发送的版本比较（`diff`），然后以操作列表的形式发送差异：

| 操作 | 含义 |
| --- | --- |
| `splice` | 在段落 `id` 的 `at` 处删除 `remove` 个字符，并插入这些带格式的 run。输入、删除、粘贴以及设置段落中部分文字的格式都是这一种操作。 |
| `split`、`join` | 在某处把一个段落拆成两段（第二段有新 id）；把两个段落合并为一段。 |
| `insert`、`delete` | 在某段之后（或开头）插入整段，或删除整段。 |
| `para` | 段落格式：只包含变化的部分，被移除的为 `null`。也包括所在的单元格和它结束的节。 |
| `table` | 表格的整体结构：行、列、宽度、合并单元格。 |
| `story` | 新建或删除页眉、页脚、脚注或文本框。 |
| `set` | 文档整体的设置：页面设置、分栏、样式、首页不同、是否开启修订。 |
| `note`、`media`、`num` | 批注、图片的字节、列表定义。 |

格式是 run 的一部分，[修订](/zh/docs/tracked-changes/)也是：开启修订时的删除会作为把文字标记为已删除的 `splice` 传送，所有人看到的都是带删除线、署有删除者姓名的文字。

该格式位于 `@rebodocs/collab` 中，完全不需要浏览器：

```ts
import { stampIds, ensureIds, diff, apply, transform } from '@rebodocs/collab';
import { importDocx } from '@rebodocs/core';

const before = stampIds(importDocx(file));
const after = ensureIds(before, editSomehow(before), mint);
const ops = diff(before, after);       // what turns one into the other
apply(before, ops);                     // the same document as `after`
```

### 所有人遵循同一顺序 {#one-order-for-everybody}

服务器为每个房间保存起始文件，以及此后每次更改的编号日志。这份日志就是所有人遵循的唯一顺序。

编辑器发送更改时会附上它看到的最后一个编号（`rev`）。如果在此期间有其他人的更改先到，服务器不会拒绝它，而是对它进行 `transform`，使它在当前文档上仍表达作者的本意，然后加入日志并通知所有人。每个编辑器按顺序应用日志中的更改，因此最终都得到同一份文档。

编辑器一次只发送一批更改，并等待它进入日志；期间输入的内容会汇集到下一批。每批都有序号，因此因回复丢失而重发的批次只会被采用一次。

### 与房间核对 {#the-check-against-the-room}

规则并不是全部。**服务器会核对每个人的文档是否一致**：更改停止片刻后（1.5 秒，持续更改时每 6 秒一次），它会用十六个字符告诉房间文档的状态：逐段汇总文字、格式和表格结构的摘要。每个编辑器对自己从房间得到的文档计算同样的摘要，如果不同，就重新加载房间：它的文件以及所有更改。用户已输入但房间还没有的内容会在其上重做并发送，因此不会丢失任何输入；可撤销的历史会重新开始。所以即使规则出了错，也只会持续几秒，而不是直到有人重新打开文档。`session.resyncs` 记录发生的次数，每次控制台也会提示。

删除会附带被删除的段落，Enter 会附带新段落的格式，格式更改会注明自己是格式：旧版编辑器发送的更改没有这些信息，仍按以前的方式处理。同一房间中不同版本的客户端可能得到不同的格式，而旧版编辑器不会与服务器核对文档，因此请同时更新编辑器和服务器。

### 编辑器如何处理这些 {#what-the-editor-does-with-it}

- **用户的操作立即显示。** 编辑器不等待服务器。当别人的更改先到时，它会被应用到服务器确认过的文档上，本人尚未确认的更改会针对它进行转换，再应用到上面。
- **撤销按人进行。** 每一步保存的是撤销它所需的更改，而不是文档原来的样子。别人的更改到达时，已保存的步骤也会针对它们进行转换，因此撤销只会撤回你做的，保留别人之后做的。
- **光标按 id 定位。** 每个人的位置以段落 id 和偏移量（以及所在部分和页面）发送，在移动后约 40 毫秒发出。更改到达时，其他人的光标会随之调整。
- **与房间核对。** 编辑器把自己的文档与服务器不时发送的摘要比较，不一致时重新加载房间（见上文）。
- **重新连接。** 连接中断时，编辑器继续工作（`state` 为 `'offline'`），并在 0.5 秒后重试，然后是 1、2、4 秒，最长 8 秒。恢复后，它会告知自己的进度；服务器只发送它缺少的部分，已发送但未得到答复的内容会重新发送。如果在此期间房间已合并进文件（见下文），或者被释放后又从你的后端重新读取，它会从头重新加载房间，离线期间输入的内容不会丢失：它根据内容识别文件中哪些段落是它原有的，把其他人在此期间所做的视为两者之间的更改，再应用之后输入的内容，就像两边同时输入一样。服务器已确认收到的内容已经在文件中，不会重复应用；可撤销的历史重新开始。房间不存在（404）、用户不再被允许进入（403）或被服务器移出（`removed`）时，会话结束。
- **自己的密钥。** 进入时，编辑器会得到一个只有它知道的密钥，它发送的所有内容都带有该密钥。其他人知道它的 id，用来绘制它的光标，但无法冒充它发送：只被允许查看的人无法把自己的更改伪装成编辑者的更改。

### 房间的生命周期 {#the-life-of-a-room}

1. **打开**：有人进入且房间里没有人时，服务器向存储请求文件（有后端时为 `GET /docs/<id>`）。
2. **有人在房间里时**，每次更改都记入内存中的日志；更改停止 `saveAfter`（默认 5 秒）后，服务器把当前文档交给后端（`PUT`），持续更改时至少每 `saveEvery`（30 秒）一次。日志累积到 `foldAfter` 次更改（1000）后，服务器会在下一次停顿时把它们合并进文件，此时大家仍在房间里：之后进入的人得到的是文件和少量更改，而不是一整天的更改。
3. **最后一个人离开时**，服务器等待 `idle`（默认 30 秒），把更改合并为一个文件，保存并释放房间。这次 `PUT` 会说明会话已结束，以及谁在其中修改了文档：[每次会话一个版本](#a-version-for-each-session)。在此期间回来的人会看到房间原样保留。
4. **关闭时**（`SIGINT`、`SIGTERM`），命令会在退出前把后端还没有的内容交给它。在你自己的程序中，请调用 `server.flush()`。

每次把更改合并进文件，房间的 `epoch` 都会增加：在合并之前就在房间里的客户端知道它的编号已失效，会重新加载。如果在有人时合并，重新读取的文件会给一些段落新的 id；服务器会告诉编辑器是哪些（`fold`），每个编辑器加载新文件，并在新 id 下应用它尚未发送的内容以及可撤销的历史。只有当文件读回来与写入它的文档一致时，服务器才会合并；否则更改会等到房间清空，与以前一样。
